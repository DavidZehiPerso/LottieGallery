Verdict

En mode A, ton exe affiche le rapport, pas Power BI. Le rapport lui-même est quasi intact ; c'est tout ce qu'il y a autour qui disparaît.

Le SDK place un seul élément (un rapport, un visuel, un tableau de bord…) dans une iframe. Tout ce qui relève de « l'application Power BI » — navigation, abonnements, alertes, Excel, Explorer, scorecards — n'existe pas dans ce cadre. Une bonne partie du confort utilisateur est récupérable, mais désactivée par défaut : il faut l'activer explicitement.

Conservé tel quel

  • Visuels, filtres, segments, synchro des segments
  • Exploration (drill) et extraction dans le rapport
  • Signets du rapport, « Personnaliser ce visuel »
  • Export des données d'un visuel, copier en image
  • RLS / OLS sur l'identité réelle, étiquettes de confidentialité
  • Audit par utilisateur

Récupérable, à activer

  • Barre d'actions (export, partage, favoris)
  • Signets personnels
  • Filtres persistants + « Rétablir les valeurs par défaut »
  • Copilot dans le rapport
  • Plein écran, zoom, mode édition, mise en page mobile

Perdu

  • Accueil, Récents, Parcourir, Apps (navigation du service)
  • Abonnements e-mail, alertes de données
  • Analyser dans Excel
  • Extraction entre rapports
  • Explorer ces données, scorecards, Teams
  • Statistiques d'utilisation fiables

En contrepartie, l'embarqué permet ce que le service ne permet pas : tes propres commandes dans le clic droit et le menu « … » d'un visuel, du code qui réagit à chaque sélection ou clic sur un bouton, des filtres pilotés par ton application, une mise en page recomposée. Ces gains viennent du SDK JavaScript : ils existent aussi dans une simple page web. Ce que seul l'exe apporte, c'est le pont vers ton logiciel et vers Windows. Détail plus bas.

Le vrai risque n'est pas fonctionnel. Il tient à trois choses : (1) Microsoft ne documente nulle part l'hébergement de Power BI dans un WebView2 d'application Windows — ni pour l'autoriser, ni pour l'interdire ; (2) l'accès conditionnel Entra peut bloquer un exe là où Edge passe ; (3) tu deviens responsable du « navigateur » : authentification, renouvellement du jeton toutes les heures, runtime, proxy, antivirus, téléchargements, impression, accessibilité.

Mode A · Pertes

Ce qui est perdu, et comment compenser

Classé par impact probable pour des utilisateurs internes habitués au service. Pour chaque perte : ce qui se passe, puis le palliatif réel (API, réglage, ou « aucun »).

Navigation du service fort

Pas d'Accueil, de Récents, de Parcourir, d'espaces de travail ni d'Apps. Le SDK n'affiche qu'un élément à la fois ; il faut écrire ton propre sélecteur de rapports. La navigation d'une app Power BI ne s'embarque nulle part, sauf dans SharePoint Online (nouveauté de novembre 2026).

usage scenario · embed for your organization
PalliatifConstruire l'arborescence avec les API REST Get Groups / Get Reports In Group (qui ne renvoient que ce que l'utilisateur a le droit de voir). Pour des rapports issus d'une app : permission Create APIs + ID de l'app dans l'URL, l'app devant être installée.

Abonnements e-mail fort

Fonction purement « service ». Aucun réglage ni API côté embarqué. Les abonnements existants continuent de fonctionner, mais les utilisateurs ne peuvent ni en créer ni en gérer depuis l'exe.

end-user-subscribe
PalliatifRenvoyer vers le service pour s'abonner, ou recréer l'envoi avec exportToFile + un planificateur / l'action Power Automate « Export to File for Power BI Reports ». Les deux exigent une capacité Fabric / Premium / Embedded — pas de PPU.

Alertes de données fort

Les alertes sur vignettes de tableau de bord et les alertes de rapport (désormais Fabric Activator, capacité F64+ ou Premium) se créent uniquement dans le service.

service-set-data-alerts
PalliatifCréer les règles Activator dans le service : elles notifient par e-mail ou Teams, indépendamment de l'exe. Aucune création d'alerte depuis l'exe.

Analyser dans Excel fort

Pas de point d'entrée dans l'iframe. Pour les profils « finance » qui vivent dans Excel, c'est souvent la perte la plus visible.

service-analyze-in-excel
PalliatifUn bouton « Ouvrir dans Power BI » qui lance Edge sur le rapport ; ou fournir directement une connexion au modèle sémantique (point de terminaison XMLA en lecture).

Extraction entre rapports fort si utilisée

La doc est explicite : « Cross-report drillthrough […] Only supported in the Power BI service. » L'extraction à l'intérieur d'un même rapport fonctionne.

desktop-drillthrough
PalliatifAjouter une commande de menu personnalisée (settings.extensions.commands + événement commandTriggered), récupérer le point de données, puis ré-embarquer le rapport cible avec filters. Faisable, mais du code par cas d'usage.

Export PDF / PowerPoint moyen

La barre d'actions embarquée permet d'« exporter » selon la doc, sans que l'inventaire exact des boutons soit publié. L'alternative programmatique, exportToFile, est asynchrone, exige une capacité (pas PPU), plafonne à 250 Mo / 50 pages, et ignore les signets personnels et les filtres persistants.

embed-for-organization · export-to
PalliatifTester d'abord la barre d'actions (bars.actionBar.visible). Pour un bouton « Exporter cette vue » fiable : bookmarksManager.capture() → passer state à exportToFile → interroger GetExportToFileStatus → télécharger. Côté exe, gérer DownloadStarting.

Explorer ces données moyen

L'expérience « Explore » est une surface du service, sans commande ni réglage dans le SDK.

explore-data-service
PalliatifAucun équivalent. Le plus proche : « Afficher sous forme de table » (seeData) ou le mode édition avec permissions: Copy.

Scorecards (métriques) moyen

« Scorecards aren't supported in embedded analytics. » Même chose pour tout élément Fabric autre qu'un rapport, tableau de bord, vignette, rapport paginé ou Q&A.

service-goals-introduction
PalliatifLien vers le service, ou reconstruire la vue KPI comme une page de rapport (sans check-ins ni permissions par objectif).

Commentaires, partage Teams moyen

La commande addComment existe dans le menu d'un visuel, mais l'embarquabilité du volet Commentaires n'est pas documentée. « Discuter dans Teams » n'a aucun réglage côté SDK.

change-visual-commands
PalliatifTester addComment dans ton tenant ; sinon renvoyer vers le service.

Statistiques d'utilisation faible à moyen

Les deux pages de doc se contredisent : l'ancien rapport d'utilisation dit ne pas compter les vues embarquées « user owns data » ; le nouveau (préversion) affiche une plateforme « Embedded ». Le journal d'activité enregistre bien ViewReport par utilisateur, avec la méthode « Embedding for your organization », sans pouvoir identifier ton appli.

service-usage-metrics · operation-list
PalliatifExtraire le journal d'activité chaque jour (rétention de 30 jours) et instrumenter l'exe toi-même (événements loaded / rendered, report.getCorrelationId()).
Mode A · Configuration

Ce qui marche, mais est désactivé par défaut

C'est le piège le plus courant : on embarque un rapport, et on conclut qu'il « manque » des fonctionnalités alors qu'elles sont simplement éteintes. Le trio indispensable : barre d'actions, scope UserState.ReadWrite.All, et les drapeaux du SDK.

Côté Entra / admin Fabric

  • Inscription d'application en plateforme « Mobile and desktop applications » — client public, jamais de secret dans l'exe. Les exemples officiels sont des applis web avec secret : non transposables tels quels.
  • URI de redirection WAM : ms-appx-web://Microsoft.AAD.BrokerPlugin/{client_id}.
  • Scopes délégués Power BI : Report.Read.All (+ Dataset.Read.All, Workspace.Read.All selon le sélecteur), UserState.ReadWrite.All (favoris, signets perso, filtres persistants), MLModel.Execute.All (Copilot).
  • Consentement administrateur accordé une fois, sinon chaque utilisateur voit une invite (ou est bloqué).
  • Paramètre de tenant « Embed content in apps » activé. Un service principal est interdit en mode A.

Côté rapport et SDK

  • Barre d'actions : settings.bars.actionBar.visible = true, ou &actionBarEnabled=true dans l'URL en mode lecture (seul le mode A la supporte en lecture). Coût : la position de la navigation des pages n'est plus pilotable par code.
  • Signets personnels : personalBookmarksEnabled: true + volet signets visible. Aucune API pour les manipuler.
  • Filtres persistants : activer dans les paramètres du rapport + persistentFiltersEnabled: true. Non modifiable après chargement.
  • Copilot : embedUrl + "&reportCopilotInEmbed=true", interrupteur Copilot du tenant, espace sur Premium ou Fabric payante.
  • Liens : hyperlinkClickBehavior: RaiseEvent, sinon chaque lien ouvre une fenêtre WebView2 orpheline.
// Configuration minimale « parité service » en mode A
const config = {
  type: 'report',
  tokenType: models.TokenType.Aad,              // jeton Entra de l'utilisateur
  accessToken: tokenFromMsal,                  // obtenu côté .NET (MSAL + WAM)
  embedUrl: report.embedUrl + '&reportCopilotInEmbed=true',
  id: report.id,
  permissions: models.Permissions.Read,
  settings: {
    bars: { actionBar: { visible: true }, statusBar: { visible: true } },
    personalBookmarksEnabled: true,
    persistentFiltersEnabled: true,
    hyperlinkClickBehavior: models.HyperlinkClickBehavior.RaiseEvent,
    localeSettings: { language: 'fr-FR' }
  },
  eventHooks: { accessTokenProvider: () => askHostForFreshToken() } // powerbi-client ≥ 2.20.1
};
Mode A · Gains

Ce que l'embarqué apporte en plus

Dans le service, le rapport est une boîte fermée : tu ne peux ni ajouter d'action, ni réagir à ce que fait l'utilisateur. Le SDK powerbi-client ouvre cette boîte dans les deux sens : ton code reçoit les événements du rapport, et peut le piloter. Les sept premiers points marchent aussi dans une page web ; le dernier est propre à l'exe.

Tes commandes dans le clic droit et le menu « … »

Ajouter des entrées au menu contextuel d'un visuel (clic droit, y compris sur un point de données) ou à son menu d'options, regroupées en sous-menus si besoin, sur tous les visuels ou seulement certains. L'événement reçu contient le visuel, la page et les points de données cliqués.

settings.extensions.commands · extend.visualContextMenu / visualOptionsMenu · groups · événement commandTriggered

extensions: { commands: [{
  name: 'ouvrirClient', title: 'Ouvrir la fiche client',
  selector: { $schema: 'http://powerbi.com/product/schema#visualSelector', visualName: 'TableClients' },
  extend: { visualContextMenu: { title: 'Ouvrir la fiche client' } }
}]}
report.on('commandTriggered', e => {
  if (e.detail.command === 'ouvrirClient') openCustomer(e.detail.dataPoints);
});

Limites : icônes seulement dans le menu « … » ; si l'en-tête du visuel est masqué, le menu « … » disparaît.

Masquer ou griser les commandes natives

Chaque commande intégrée (exporter les données, tri, spotlight, extraction, afficher sous forme de table, ajouter un commentaire…) peut être activée, grisée ou masquée, globalement ou visuel par visuel, et modifiée en cours de session.

settings.commands (Enabled / Disabled / Hidden) · sélecteurs · report.updateSettings()

Limite : le mode focus n'a pas de commande propre ; on ne peut que masquer tout l'en-tête.

Réagir à ce que fait l'utilisateur

Un bouton du rapport peut déclencher ton code ; une sélection dans un visuel peut mettre à jour ton interface ; un changement de page peut être journalisé. Tu peux aussi remplacer la boîte « Enregistrer sous » par la tienne.

buttonClicked · dataSelected (filtres + points) · visualClicked · selectionChanged · pageChanged · dataHyperlinkClicked · exportDataCompleted · saveAsTriggered · rendered

Piloter le rapport depuis ton application

Appliquer des filtres et l'état des segments selon le contexte de ton appli (client ouvert, site, période), changer de page, appliquer ou capturer un signet, changer de thème, de zoom ou de langue. L'utilisateur arrive directement sur la bonne vue.

setFilters / updateFilters · visual.setSlicerState · setPage · bookmarksManager.apply / capture · applyTheme · setZoom

Attention : un filtre d'URL ou de code n'est pas une sécurité. La restriction des données passe par la RLS.

Recomposer la page

Changer la position, la taille et la visibilité des visuels sans toucher au rapport publié ; adapter la disposition à la taille de la fenêtre ; laisser l'utilisateur choisir ses visuels. Ou embarquer des visuels isolés de plusieurs rapports sur un même écran.

layoutType: Custom + customLayout.pagesLayout · type: 'visual'

Créer ou modifier des visuels à la volée

Changer le type d'un visuel, ajouter ou retirer des champs, créer un visuel depuis ton interface, sans que l'utilisateur connaisse Power BI. Microsoft en fait une démonstration (« Quickly create personalized visuals »).

Bibliothèque powerbi-report-authoring : createVisual, changeType, addDataField

Limite : uniquement les visuels natifs ou déjà installés dans le rapport.

Ton habillage, tes messages

Masquer les volets, remplacer la navigation par la tienne, masquer les messages d'erreur Power BI pour afficher les tiens, intégrer le rapport dans ta charte.

settings.panes · hideErrors: true + événement error

Récupérer les données affichées

Lire les données d'un visuel filtré pour alimenter une action : c'est exactement la démo Microsoft « Go from insights to quick action », où un clic droit sur une liste de clients lance une campagne avec les clients filtrés.

visual.exportData(ExportDataType.Underlying)

Limite : 30 000 lignes, CSV, et pas pour les visuels utilisant des mesures du modèle ou du rapport.

Propre à l'exe : le pont vers ton logiciel et vers Windows

C'est le seul gain qu'une page web n'a pas. Une commande de clic droit peut appeler ton code .NET : ouvrir l'écran correspondant dans ton logiciel métier, écrire un fichier local, imprimer sur une imprimante métier, lancer un processus, ou à l'inverse transmettre au rapport le contexte de ce que l'utilisateur fait dans ton appli. C'est l'argument le plus solide pour construire un exe.

Page → .NET : window.chrome.webview.postMessage() + événement WebMessageReceived · .NET → page : PostWebMessageAsJson()

// dans la page
report.on('commandTriggered', e => window.chrome.webview.postMessage({ action: e.detail.command, points: e.detail.dataPoints }));
// côté C#
webView.CoreWebView2.WebMessageReceived += (s, a) => HandleReportAction(a.WebMessageAsJson);

Ces gains compensent aussi certaines pertes : une commande personnalisée peut reconstruire l'extraction entre rapports, un bouton peut lancer un export PDF de la vue courante. Mais chacun représente du code à écrire et à maintenir. Si tu n'en exploites aucun, l'embarqué ne t'apporte que des pertes ; si tu en exploites plusieurs, il devient nettement plus riche que le service.

Sources : change-visual-commands · handle-events · custom-layout · report-authoring-overview · showcase insights to action · WebView2 web/native interop

Supportabilité

Est-ce supporté par Microsoft ?

Réponse honnête : ni oui ni non — c'est non documenté. Voici où se situe ton scénario et sur quoi repose cette conclusion.

Explicitement non supporté

Secure embed (code « Site web ou portail ») dans une appli : « The automatic authentication capabilities don't work when they're embedded in applications, including in mobile and desktop applications. » À écarter.

Explicitement non supporté

Applications mobiles hébergeant Power BI dans une WebView : « Embedding Power BI content in mobile applications that host web content through web components, embedded browser controls, or WebViews isn't supported. » La phrase vise les applis mobiles, mais nomme exactement le type de contrôle qu'utiliserait ton exe.

Non documenté — ton cas

Mode A dans une WebView2 d'application Windows. Aucune page ne l'autorise ou ne l'interdit. La liste des navigateurs supportés cite seulement Edge 120+, Chrome, Safari et Firefox. Tous les exemples officiels sont des applis web. À l'inverse, Power BI Desktop lui-même repose sur WebView2 : le moteur n'est pas le problème.

Non documenté, plus risqué

Mode E (WebView2 sur app.powerbi.com). Mêmes silences, plus un accès conditionnel démontré comme fragile (WebView2 absent de la liste Entra des navigateurs pour « appareil conforme », bug #5595 ouvert en juin 2026). Et Microsoft a retiré sa propre appli Power BI pour Windows le 31 décembre 2023 en renvoyant vers le navigateur.

Supporté

Mode A dans une page web ouverte dans un navigateur supporté — le scénario des exemples Microsoft.

Conséquence pratique : en cas de bug spécifique à l'hôte, le support te demandera de reproduire dans Edge. Si l'exe doit être un produit durable, obtiens une confirmation écrite via ton account team ou un ticket de support avant d'engager le développement.

Coûts récurrents

Licences et capacité en mode A

L'embarquement ne change pas la licence nécessaire : « There's no specific licensing requirement to embed for your organization. » Chaque utilisateur a besoin du même droit que pour ouvrir le rapport dans le navigateur.

  • Contenu sur Fabric F64+ ou Premium P : une licence Fabric gratuite suffit pour consulter.
  • En dessous de F64, ou sur une SKU A : Pro ou PPU pour chaque lecteur.
  • Service principal interdit en mode A : impossible de faire tourner l'exe sous un compte applicatif pour éviter les licences. Un exe ne réduit en rien le besoin de licences.
  • exportToFile (export programmatique, abonnements maison) : capacité Fabric, Premium ou Embedded obligatoire ; non supporté en PPU pour les rapports Power BI.
  • Copilot : capacité Premium ou Fabric payante + interrupteur Copilot du tenant.
  • Chaque export et chaque rendu consomme des CU de la capacité ; à suivre dans l'application Fabric Capacity Metrics.

Les prix publics actuels (Pro, PPU, F SKU) n'ont pas été revérifiés pendant cette recherche : consulte la page tarifaire Microsoft avant de chiffrer.

Options

Alternatives à évaluer avant de coder

Commence par te demander pourquoi tu veux un exe. Selon la motivation, une option sans code donne souvent le même résultat sans aucune perte.

Edge « Installer ce site en tant qu'application »

Fenêtre dédiée, icône dans la barre des tâches et le menu Démarrer, sans barre d'adresse. Déployable à tout le parc par stratégie (WebAppInstallForceList).

0 perte 0 code navigateur supporté. Ne remplace pas : l'intégration avec une appli métier locale.

Apps d'organisation Fabric (GA)

Regrouper plusieurs rapports avec navigation, sections, icône, couleur et audiences. Filtres persistants activés par défaut.

supporté répond au besoin « mes rapports avec ma navigation ». Le chrome Fabric reste visible (mode Focus par session).

Composant WebPart Power BI de SharePoint Online

Portail interne avec SSO, RLS, et interrupteurs pour la navigation, le volet filtres et la barre d'actions. Depuis novembre 2026, une app d'espace de travail complète peut y être embarquée.

quelques pertes pas d'invités B2B dans le composant.

Application Power BI dans Teams

Presque tout le service, hébergé et supporté par Microsoft dans une appli de bureau — c'est la version « officielle » de l'idée d'un exe.

quelques pertes pas de filtres d'URL ni de signets personnels dans les onglets.

Hors connexion : impossible dans un exe. Seules les applis mobiles iOS/Android mettent en cache (modèles importés uniquement, 250 Mo). Un exe WebView2 n'apporte aucune capacité hors ligne ; le seul artefact consultable sans réseau est un fichier produit par exportToFile.

Décision

Recommandation

Le mode A vaut le coup si tu exploites ses personnalisations ; l'exe vaut le coup si tu as besoin du pont vers un logiciel de bureau. Sinon, l'un comme l'autre ne t'apportent que des pertes.

Si l'objectif est « une appli dédiée à nos rapports », Edge installé en tant qu'application + une app d'organisation donnent le résultat sans aucune perte, sans code et dans un cadre supporté. Si l'objectif est d'afficher des rapports dans un logiciel métier, avec un contexte transmis (client sélectionné → filtre du rapport), alors le mode A dans une WebView2 est le bon choix — à condition de l'assumer comme une page web hébergée dans un shell fin, avec un bouton « Ouvrir dans Power BI » vers Edge pour tout ce qui est perdu. Le mode E est à réserver à un usage interne ponctuel, pas à un produit.

Tu veux surtout une fenêtre dédiée, une icône, ta marqueEdge « installer en tant qu'application » + app d'organisation. Pas d'exe.
Tu veux regrouper plusieurs rapports avec ta navigationApp d'organisation Fabric, ou portail SharePoint. Pas d'exe.
Tu veux des actions métier au clic droit, réagir aux sélections, recomposer les pages — sans lien avec un logiciel localMode A, mais dans une application web interne (supportée, sans runtime ni installeur). L'exe n'apporte rien de plus ici.
Tu veux intégrer des rapports dans un logiciel de bureau existant, filtrés selon son contexteMode A en WebView2, MSAL + WAM, renvoi vers le service pour les fonctionnalités perdues.
Tes utilisateurs dépendent des abonnements, des alertes, d'Excel ou de l'extraction entre rapportsGarde le service comme surface principale ; l'exe ne serait qu'un complément.
Ton tenant impose « Exiger une stratégie de protection d'application »Bloquant pour tout exe maison. Seuls Edge et Windows App satisfont cette règle.
Tu as besoin du hors-connexionAucun exe ne le fournira. PDF exportés, ou applis mobiles.

Si tu construis quand même : l'ordre des travaux

  1. Vérifier les bloqueurs avant d'écrire une ligne : stratégies d'accès conditionnel, paramètre de tenant « Embed content in apps », Private Link (qui coupe l'export PDF/PPT et Copilot), capacité disponible.
  2. Prototype jetable : WebView2 + page SDK + jeton MSAL/WAM, testé sur un poste réel du parc (proxy, antivirus, accès conditionnel). C'est là que les projets meurent, pas dans le code Power BI.
  3. Inscription Entra en client public, scopes, consentement administrateur.
  4. Renouvellement du jeton via accessTokenProvider, cache MSAL persistant.
  5. Activation de la barre d'actions, des signets personnels, des filtres persistants, de Copilot si capacité.
  6. Sélecteur de rapports via l'API REST ; bouton « Ouvrir dans Power BI ».
  7. Plomberie WebView2 : dossier de données, hôte virtuel, popups, téléchargements, impression, clavier, langue, DPI.
  8. Installeur signé + bootstrapper du runtime, mise à jour automatique, documentation IT (URL, exclusions antivirus).
  9. Journalisation des IError, mode support, extraction quotidienne du journal d'activité.

Ordre de grandeur, estimation personnelle non sourcée pour un développeur .NET à l'aise avec le web : 3 à 5 semaines pour une version fiable, puis quelques jours par trimestre pour suivre WebView2, le SDK et les changements du service.

Les questions qui changeraient cette recommandation

  • Tes rapports sont-ils sur une capacité F64+ / Premium ? (export programmatique, Copilot, lecteurs en licence gratuite)
  • Quelles stratégies d'accès conditionnel s'appliquent à l'application Power BI dans ton tenant ?
  • L'exe doit-il échanger du contexte avec un logiciel local, ou seulement afficher des rapports ?
  • Tes utilisateurs se servent-ils aujourd'hui des abonnements, des alertes, d'Analyser dans Excel ou de l'extraction entre rapports ?
  • Le tenant utilise-t-il Private Link ?

Méthode et limites

Recherche menée les 19 et 20 novembre 2026 par plusieurs agents en parallèle, chacun sur un axe (limites officielles, fonctionnalités de consommation, export, authentification, runtime WebView2, gouvernance, alternatives), avec l'obligation de ne citer que des pages effectivement consultées. Environ 140 constats, principalement issus de Microsoft Learn, complétés par les dépôts GitHub WebView2Feedback et PowerBI-JavaScript.

Ce qui n'a pas été fait : la passe de vérification contradictoire automatique a été interrompue, de même que les axes « licences et prix », « architecture de référence » et « évolution du SDK ». Pour compenser, j'ai revérifié moi-même dans la doc actuelle les affirmations qui pèsent le plus sur la décision : la phrase sur les WebViews (et sa portée limitée au mobile), les fonctionnalités réservées au mode A et leurs prérequis, l'extraction entre rapports réservée au service, et les limites d'exportToFile (capacité, PPU, signets personnels).

Non couvert ou incertain : prix publics actuels ; position contractuelle des conditions d'utilisation sur un shell tiers ; inventaire exact des boutons de la barre d'actions embarquée ; comportement réel des infobulles de page et du volet Commentaires en embarqué. Les cases « à tester » de la matrice signalent ces zones.
